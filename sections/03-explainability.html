Explaining Data Pipelines

Building on the previous foundations, we present two representative examples. The first presents a baseline data lineage scenario, illustrating how individual output tuples produced through common operations such as selection, projection, join, union and aggregation, can be traced back to the source data that contributed to their derivation. The second case introduces a root-cause analysis for an employee promotion prediction model. It puts in evidence how intermediate data outside the training dataset can quietly condition model results, and how provenance polynomials allow to trace the underlying pathways through diverse perspectives, namely the data and the pipeline methods themselves. This provides the means to analyze the upstream data preparation to detect fairness anomalies that favor or prejudice specific employee groups, and isolate their root causes. While algebraic annotations precisely capture data dependencies, they can become hard to interpret in large datasets or complex pipelines. To overcome this, we complement our algebraic representation with graphical visualizations, making data derivation paths and their underlying dependencies easier to understand. Importantly, the provenance-based analysis is model agnostic, remaining independent of the predictive model itself.

Lineage

Lineage is the most basic form of data provenance. It identifies the input tuples that contributed to a given output record, establishing a direct link between source and derived data and providing a lightweight way to trace how data flows across processing pipelines. This simple representation allows the origins of a result to be traced back to its source records and makes data dependencies easier to understand.

Lineage can be captured during query execution or derived on demand from richer, fine-grained provenance representations, such as provenance polynomials or semiring annotations. For example, in a database query joining a customer table with a transaction log, fine-grained provenance might record the exact join condition and feature scalings applied ($t_1 \cdot t_2$). In contrast, lineage simplifies this result into the minimal source set specifying simply that output record $R_1$ was derived from Customer tuple $C_{104}$ and Transaction tuple $T_{892}$.


EXAMPLE: This simple representation makes it possible to trace the origins of query results or datasets used for data analytics and machine learning. It allows users to identify which data items contributed to a particular result and, conversely, to determine which results were influenced by a given source. For example, it can be used to identify the training courses that contributed to the most popular courses in a dataset. Moreover, provenance tracking can capture intermediate data items that do not appear in the final query result but were necessary to compute it, revealing dependencies that may also affect downstream analytics and machine learning processes. Furthermore, it tracks intermediate data that, while absent from final outputs, remains critical for calculations and downstream machine learning workflows.


While lineage identifies which source tuples contributed to a result, provenance polynomials provide a richer explanation of how and why those tuples contributed by capturing the structure of their derivations, including alternative and joint contributions. For aggregate queries, semimodule annotations further associate each contributing tuple with the value it contributes to the aggregate, making it possible to determine not only which tuples influenced the result, but also how their individual values contributed to the final aggregate.

Debugging and Influence functions

A concrete example is to detect whether employees are effectively evaluating themselves in a promotion prediction pipeline. For instance, an employee’s performance record may be used both as an input to the training data and, directly or through intermediate transformations, as the basis for the target or evaluation features. Techniques such as influence functions can help quantify how much a specific training record affects a model prediction, answering questions such as: How much would this prediction change if a particular training record were removed or slightly modified? This can help identify erroneous or suspicious predictions, mislabeled data, data poisoning, and records with disproportionate influence.

Influence functions complement, rather than replace, relational data provenance. While provenance polynomials precisely trace which source records and operations produced a data item, influence functions capture the continuous statistical or gradient-based impact of training records on model outputs. Combining both perspectives can therefore connect an anomalous prediction to its upstream data lineage while also quantifying how strongly individual records influenced the model's decision.
